# Post-mortem INC-2025-0175: Kafka consumer group rebalance storm - CommitFailedError

| Field | Value |
|---|---|
| Date | 2025-05-06 |
| Service | `orders-worker` |
| Environment | production |
| Severity | SEV3 |
| Duration | 140 minutes |

## Summary
Order confirmation emails delayed up to 2 hours; 300 duplicate emails sent. Trigger: Slow handler made batches exceed max.poll.interval.ms.

## Detection
Consumer lag alert > 50k messages.

## Timeline (UTC)
- 13:00 New PDF invoice generation added to the order handler (~3 s per message).
- 13:20 Lag climbs; logs show CommitFailedError and rebalances.
- 15:20 max_poll_records reduced to 50 and handler made idempotent; lag drains.

## Error Signatures Observed
```text
kafka.errors.CommitFailedError: CommitFailedError: Commit cannot be completed since the group has already
rebalanced and assigned the partitions to another member. This means that the time between subsequent calls
to poll() was longer than the configured max_poll_interval_ms
WARNING Heartbeat failed for group orders-worker because it is rebalancing
```

## Root Cause Analysis
**Trigger:** Slow handler made batches exceed max.poll.interval.ms.

A batch took longer to process than `max.poll.interval.ms` (default 300 s), so the broker evicted the
consumer and reassigned partitions. The slow consumer's commit then failed, the batch was redelivered,
and the cycle repeated.

## Resolution
Smaller batches, idempotent handler, invoice generation moved to its own queue.

## Action Items
| # | Action | Status |
|---|---|---|
| 1 | Lag-based autoscaling with KEDA (owner: platform). | Open |

## Lessons Learned
Consumers must poll regularly; slow work belongs in its own queue.
