# Post-mortem INC-2025-0156: Redis socket timeouts in auth-service caused by a blocked Redis

| Field | Value |
|---|---|
| Date | 2025-04-28 |
| Service | `auth-service` |
| Environment | production |
| Severity | SEV2 |
| Duration | 18 minutes |

## Summary
Logins failed intermittently for 18 minutes; 9% error rate. Trigger: A cron job used KEYS instead of SCAN on a large production keyspace.

## Detection
auth-service 5xx alert and Redis latency alert.

## Timeline (UTC)
- 11:00 Analytics cron job runs `KEYS session:*` against production Redis (2.1M keys).
- 11:01 auth-service logs `redis.exceptions.TimeoutError: Timeout reading from socket`.
- 11:09 SLOWLOG reveals KEYS taking 1.8 s per call, repeated every few seconds.
- 11:17 Cron job disabled; latency returns to < 1 ms.

## Error Signatures Observed
```text
{"level": "ERROR", "service": "auth-service", "logger": "auth.api", "msg": "unhandled error on POST /login", "exc_type": "redis.exceptions.TimeoutError", "exc_message": "Timeout reading from socket"}
{"level": "WARNING", "service": "auth-service", "logger": "auth.access", "msg": "POST /login 500", "duration_ms": 1003.2}
```

## Root Cause Analysis
**Trigger:** A cron job used KEYS instead of SCAN on a large production keyspace.

Redis is single-threaded for commands. One expensive command (`KEYS *` on millions of keys, a big
`DEL` of a huge set, a Lua script, or a `CLIENT PAUSE` during a failover) blocks every other client. The
auth-service rate-limiter and session writes then exceed the 1 s `socket_timeout` and raise
`redis.exceptions.TimeoutError`. The connection is fine; the server is busy.

## Resolution
Disabled the job, rewrote it with SCAN, renamed KEYS in production config, made the rate limiter fail-open.

## Action Items
| # | Action | Status |
|---|---|---|
| 1 | Rename KEYS/FLUSHALL in production Redis (owner: platform). | Open |
| 2 | Fail-open rate limiter (owner: auth team). | Open |

## Lessons Learned
One O(N) command can stall a single-threaded Redis for every client.
