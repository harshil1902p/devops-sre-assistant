# Post-mortem INC-2025-0211: Postgres rejects connections with 'too many clients already'

| Field | Value |
|---|---|
| Date | 2025-06-03 |
| Service | `payments-api` |
| Environment | production |
| Severity | SEV1 |
| Duration | 22 minutes |

## Summary
Card payments failed for 22 minutes during a marketing campaign; 2,300 failed checkouts. Trigger: Autoscaling multiplied per-pod connection pools beyond Postgres max_connections=200.

## Detection
Synthetic checkout probe failed; Postgres log alert on FATAL errors.

## Timeline (UTC)
- 09:05 Campaign traffic starts; HPA scales payments-api 6 -> 20 pods.
- 09:12 `FATAL: sorry, too many clients already` in Postgres logs.
- 09:19 On-call caps HPA at 8 replicas; terminates idle sessions.
- 09:27 Checkout success rate recovers.

## Error Signatures Observed
```text
psycopg.OperationalError: connection failed: connection to server at "10.0.4.12", port 5432 failed: FATAL:  sorry, too many clients already
psycopg.OperationalError: connection failed: FATAL:  remaining connection slots are reserved for non-replication superuser connections
2025-06-03 09:14:55 UTC [3121]: FATAL:  sorry, too many clients already
```

## Root Cause Analysis
**Trigger:** Autoscaling multiplied per-pod connection pools beyond Postgres max_connections=200.

Postgres has a hard server-side limit, `max_connections`. Every application replica opens up to
`pool_size + max_overflow` connections, so total demand is `replicas x (pool_size + max_overflow)` plus
cron jobs and admin tools. When the HPA scaled payments-api from 6 to 20 pods, demand exceeded
`max_connections=200` and Postgres refused new clients.

## Resolution
Capped replicas, then deployed PgBouncer in transaction mode and reduced per-pod pools.
