# Post-mortem INC-2025-0142: SQLAlchemy QueuePool exhaustion in auth-service

| Field | Value |
|---|---|
| Date | 2025-04-12 |
| Service | `auth-service` |
| Environment | production |
| Severity | SEV2 |
| Duration | 47 minutes |

## Summary
18% of logins failed with HTTP 500 for 47 minutes during the Saturday peak; ~4,100 users affected. Trigger: A new synchronous audit-report query ran inside the login request and held a pooled connection for 20-30 seconds.

## Detection
PagerDuty alert on auth-service 5xx rate > 5% for 5 minutes.

## Timeline (UTC)
- 14:02 Deploy of auth-service v2.31 adds the /login audit-report query.
- 14:09 5xx alert fires; on-call sees `QueuePool limit of size 5 overflow 2 reached` in logs.
- 14:21 Postgres confirmed healthy (12% CPU, 40/200 connections), so the problem is client-side.
- 14:35 pg_stat_activity shows audit-report queries running 20-30 s each, holding pooled connections.
- 14:44 Rollback to v2.30; pool recovers within 1 minute.
- 14:49 Error rate back to baseline; incident resolved.

## Error Signatures Observed
```text
{"level": "ERROR", "service": "auth-service", "logger": "auth.api", "msg": "unhandled error on POST /login", "exc_type": "sqlalchemy.exc.TimeoutError", "exc_message": "QueuePool limit of size 5 overflow 2 reached, connection timed out, timeout 5.00 (Background on this error at: https://sqlalche.me/e/20/3o7r)"}

{"level": "INFO", "service": "auth-service", "logger": "auth.runtime", "msg": "runtime stats (db pool: Pool size: 5  Connections in pool: 0 Current Overflow: 2 Current Checked out connections: 7)"}
```

## Root Cause Analysis
**Trigger:** A new synchronous audit-report query ran inside the login request and held a pooled connection for 20-30 seconds.

Every request needs a connection from SQLAlchemy's client-side `QueuePool`. The pool allows
`pool_size` (5) persistent connections plus `max_overflow` (2) temporary ones. When all 7 are checked out,
new requests wait `pool_timeout` seconds and then raise `sqlalchemy.exc.TimeoutError`.
Connections stay checked out because some code path holds them for a long time: slow queries, sessions
that are never closed, or long transactions wrapping remote calls. The database is not the
bottleneck; the **client pool** is.

## Resolution
Rolled back v2.31. Follow-up: increased pool_size to 20 and max_overflow to 10 in database.py, moved the audit report to an async worker, and set statement_timeout=3s.

## Lessons Learned
When requests fail after exactly pool_timeout seconds and the database looks idle, the bottleneck is the client connection pool, not Postgres.
