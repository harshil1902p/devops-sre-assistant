# Post-mortem INC-2025-0233: notification-service cannot connect to Redis - ECONNREFUSED

| Field | Value |
|---|---|
| Date | 2025-06-21 |
| Service | `notification-service` |
| Environment | production |
| Severity | SEV2 |
| Duration | 31 minutes |

## Summary
Push notifications delayed by up to 31 minutes. Trigger: Client configured with a pod IP instead of the Kubernetes Service name.

## Detection
Queue-depth alert on notifications.

## Timeline (UTC)
- 08:02 Node pool upgrade reschedules the Redis pod to a new IP.
- 08:03 notification-service logs `connect ECONNREFUSED 10.0.3.15:6379`.
- 08:25 Engineer finds REDIS_HOST set to the old pod IP in a ConfigMap.
- 08:33 ConfigMap updated to service DNS; pods restarted; backlog drains.

## Error Signatures Observed
```text
[ioredis] Unhandled error event: Error: connect ECONNREFUSED 10.0.3.15:6379
    at TCPConnectWrapper.afterConnect [as oncomplete] (node:net:1555:16)
{"level":"error","service":"notification-service","msg":"queue publish failed","err":"Connection is closed."}
```

## Root Cause Analysis
**Trigger:** Client configured with a pod IP instead of the Kubernetes Service name.

Nothing is listening on the target IP/port: Redis pod was OOMKilled and restarting, or the client
hard-coded a pod IP that changed after rescheduling instead of using the Service DNS name.

## Resolution
Use Service DNS; add retryStrategy.

## Action Items
| # | Action | Status |
|---|---|---|
| 1 | Lint ConfigMaps for raw pod IPs (owner: platform). | Open |

## Lessons Learned
Pod IPs are ephemeral; always address workloads through Services.
