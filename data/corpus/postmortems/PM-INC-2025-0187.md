# Post-mortem INC-2025-0187: Postgres deadlocks between concurrent payment transactions

| Field | Value |
|---|---|
| Date | 2025-05-14 |
| Service | `payments-api` |
| Environment | production |
| Severity | SEV3 |
| Duration | 95 minutes |

## Summary
0.7% of internal transfers failed and had to be retried manually. Trigger: Reconciliation job updated accounts in descending id order while the API used ascending order.

## Detection
Error-budget burn alert on the transfers endpoint.

## Timeline (UTC)
- 10:10 Spike of 40P01 errors after a batch reconciliation job starts.
- 10:40 Team identifies opposite lock ordering between the job and the API.
- 11:45 Hotfix adds ordered locking; errors stop.

## Error Signatures Observed
```text
psycopg.errors.DeadlockDetected: deadlock detected
DETAIL:  Process 4121 waits for ShareLock on transaction 99812; blocked by process 4188.
Process 4188 waits for ShareLock on transaction 99807; blocked by process 4121.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (12,7) in relation "accounts"
```

## Root Cause Analysis
**Trigger:** Reconciliation job updated accounts in descending id order while the API used ascending order.

Two transactions lock the same rows in opposite order (A then B vs B then A). Postgres detects the
cycle after `deadlock_timeout` and aborts one transaction.

## Resolution
Deterministic lock ordering in both code paths plus retry on 40P01.

## Action Items
| # | Action | Status |
|---|---|---|
| 1 | Add retry decorator for serialization/deadlock errors (owner: payments). | Open |

## Lessons Learned
Deadlocks are a design bug in lock ordering, not a capacity problem.
